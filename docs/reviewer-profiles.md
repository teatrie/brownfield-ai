# Reviewer Profiles — Strengths and Use Cases

Lean recommendations for cross-model code review orchestration. Records observed strengths of each reviewer type and prescribes which reviewers to include for each work class.

**Companion**: [reviewer-history.md](./reviewer-history.md) — per-cycle log with evidence backing the recommendations here. Do not load the history doc into an agent's context just to decide reviewer selection; load this file instead. Update the history doc after every multi-reviewer cycle; update this file only when the log accumulates enough cycles to shift a recommendation.

### Where each reviewer should always be included

**Legend**: **M** = mandatory (include every time); **R** = recommended (include unless cost-constrained); **O** = optional (include when the case calls for it); **—** = typically not helpful.

**Rubric scope**: dimensions 1–10 are the shared block every reviewer template carries; 11–21 are diff-only. Where this file counts *this repo's* rubric, 10 is that shared block and is not a stale figure — only the QA diff-review row below is scoped to all 21. The Codex-builtin rows are not counting this repo's rubric at all: their **native 10-point review** is codex's own built-in one, unrelated to this numbering.

The **Codex-builtin** column is `—` on every row for a different reason than the legend's: the axis has no invocation path, so there is nothing to dispatch at any designation. See the roster note above and **TODO-0207**.

| Use case | Opus | Gemini | Codex-custom | Codex-builtin |
|---|---|---|---|---|
| **Planning review** (architecture, design decisions, vertical-slicing plans) | **M** | O (only if plan affects security / sandbox / regex logic) | **M** (multi-phase plans — cross-phase integration, dropped predecessor requirements) / **R** (single-phase plans — shim config, wiring, env vars) | — |
| **Wave step code review** (implementation quality, standards, SOLID) | **M** | **R** (mandatory for security-adjacent code: hooks, regex, auth, sandbox) | O (mandatory for shim/CLI/config-heavy waves) | — |
| **Spec verification** (does implementation match plan/spec) | **M** | — (limited value for non-security specs) | **R** (catches spec drift in config and wiring) | — |
| **QA diff-review** (the full gate: all 21 standard dimensions, cross-model) | **M** | **M** (non-negotiable for security-adjacent diffs; strong-recommended for everything else) | **R** (broad surface-area coverage) | — |
| **Regression-guard review** (review of a test / assertion whose purpose is to catch a specific regression class — does the guard hold against bypasses of the abstract threat?) | **M** (rubric + traceability to the stated regression instance) | **M** (bypass-vector enumeration on the guard — the finding class Opus systematically underweights here) | O (only when the guard wires into a shim / config surface) | — |

### Rationale for mandatory designations

- **Opus** is mandatory across the board because its rubric adherence is the baseline quality floor. Even when it doesn't find the blocker, it reliably covers the standard 10 shared dimensions and anchors the review record.
- **Gemini** is mandatory for QA diff-review because the history shows it uniquely catches code-execution bypasses that the other three miss. For security-heavy waves, escalating its role to mandatory during wave review is cheap insurance.
- **Codex-builtin** carries no designation, because it has no invocation path — not because the axis lacks value. Its evidence stands and is the reason **TODO-0207** exists: on `qa/cli-args-shim-r1` it uniquely surfaced four different workflow-integration gaps (G4, G5, G7, Hβ) across four rounds, none of which any of the other three reviewers caught, and cross-file migration drift (agent docs, workflow prompts, cross-directory legacy forms) is an axis no remaining reviewer is characterized for. Note the scope of that evidence: it comes from diff review only. The native-review path was selected only for `REVIEW_TYPE=diff`, so planning and spec-verification never reached this reviewer — the designations they carried were unachievable for as long as they stood, and no working capability was lost there.
- **Codex-custom** is mandatory for **multi-phase plan integration reviews** (TODO-0089/0090/0092 epic family — Codex-custom was the dominant plan-reviewer of record; uniquely caught structural integration gaps like cross-phase timing contradictions and dropped predecessor requirements). Otherwise its strengths (shim wiring, dead knobs, allowlist gaps) are more narrowly-scoped — for CLI/config/shim-heavy diffs it's a strong recommend; for pure business-logic code it's lower value than the other three. **Note**: Codex carries unique single-reviewer signal on **library/runtime-semantics contract correctness** at any diff size — Entry 3 (218 / 81-line late rounds: JSON-key collision, default-id regression) and Entry 4 (2129-line first round: RecursionError-escapes-CB, tautological-asdict-assertion). The pattern: when the verdict turns on understanding library/runtime projection rules (`dataclasses.asdict`, `json` recursion depth, regex flags, exception-class coverage), Codex catches what exhaustive-rubric reviewers miss because they read the test/code at face value rather than against the library's actual semantics. **Heuristic**: drop Codex at your peril for any diff with library/runtime-semantics surface — not only at small-diff late rounds but at large first-round diffs too, where the size-was-the-discriminator framing previously suggested Codex was lower-value.
- **Regression-guard review** makes Gemini mandatory for a new reason beyond security-adjacent code. On `qa/hook-registration-integrity-001`, Gemini Flash MEDIUM caught the only HIGH finding (V6 = settings.local.json TOCTOU — same abstract threat class as the original TODO-0083) while Opus HIGH confirmed only the stated instance. The complementarity pattern: Opus covers "does the guard fire on the case that motivated it" (traceability); Gemini covers "can the guard be bypassed by an adjacent variant of the same threat class" (enumeration). Both are load-bearing — neither subsumes the other.

### Orchestration notes

- **Always dispatch in parallel.** Cross-model value depends on independent analysis; sequential review contaminates later reviewers with earlier reviewers' framing.
- **Custom prompts require repetition of key security questions.** The Codex-custom agent has a tendency to drift to codex's default framing when the custom prompt isn't structurally distinct. If a specific regex trace or exploit class is the critical question, state it explicitly and near the top of the prompt.
- **Deny settings must be temporarily removed before dispatching reviewer subagents** when the review subject includes `.sh` files, hooks, or `.claude/settings.json`. The reviewers need to Read those files; a residual `Edit` deny blocks some of their Read operations on some toolchains. See `qa/cli-args-shim-r1` workflow for the explicit unblock/restore pattern.
- **Bridge agents frequently fail to save review artifacts to disk** due to their own Write-tool absence + sandbox constraints. The orchestrator must capture the inline review text from the subagent result and persist it using the main-session Write tool. Plan for this in every QA cycle.
- **Effort tier selection**: the roster above captures both the `high` tier and the `medium` (baseline agent, no effort suffix) tier for each reviewer. `xhigh` / `max` variants exist; most profiles remain uncharacterized — add rows to the roster table when used. The Codex MAX tier is the first characterized exception (see next bullet).
- **Codex MAX tier model selection (2026-04-24)**: operator selects `gpt-5.5` in local OAuth mode and MUST select `gpt-5.4` in container (API-key) mode — gpt-5.5 is currently OAuth-only in Codex CLI, and the wrapper does NOT auto-downgrade on auth failure — the `ERROR_CLASS="auth"` branch in `scripts/agent-cli/codex-review.sh` emits `CODEX_ERROR` with `error_class=auth` and stops, but it **exits 0**, so callers must read `tmp/codex-exit.json` rather than the process exit status. gpt-5.5 wins on Terminal-Bench 2.0 and Expert-SWE long-horizon coding but is 2× the per-token cost of gpt-5.4 ($5/$30 vs $2.50/$15 per 1M tokens), so MAX tier is reserved for low-volume frontier reviews. No `gpt-5.5-codex` SKU exists yet, so the MEDIUM/HIGH tiers are unchanged. See [codex-reviewer.md](../.claude/agents/codex-reviewer.md#model-selection-matrix) for the full matrix.
- **Regression-guard review — prompt both instance and class**: when the review subject is a test guarding against a regression, state both the original regression instance AND the abstract threat class in the prompt. Opus reliably confirms the instance but systematically underweights the class (observed on `qa/hook-registration-integrity-001`: confirmed the test catches the settings.json rewrite to nonexistent path, missed the same TOCTOU shape in settings.local.json). Gemini generalizes naturally. Framing the prompt to ask both questions explicitly lets reviewers become complementary rather than accidentally overlapping.
- **Tri-family escalation heuristic**: dual-family (Claude default) suffices for most diffs, but **escalate to tri-family for any diff with regex / network classification / contract-correctness semantics** even when the diff is small. Evidence: TODO-0092d-polish r1 (281-line staged) was originally dual-family; user escalated to tri-family and Gemini caught a load-bearing regex DRY violation that would have shipped under dual. Entry 3 (findings:apply-batch r3 + r4) saw Codex carry single-reviewer signal at 218 / 81-line diffs — both load-bearing contract regressions Opus + Gemini missed.
- **Pre-commit absorption vs re-review**: when r1 verdicts are unanimous APPROVED-WITH-NOTES and findings are local polishes, fold fixes into a single r2 commit without spawning a second review round (TODO-0092 Phase C and Phase D both used this pattern successfully). When findings have **architectural implications** (atomic semantics, deepcopy strategy, contract-surface changes), spawn a fresh review round on the resulting redesign — Entry 3 R1→R5 used the latter throughout because each round's fixes touched the contract surface. **Heuristic**: re-review when fixes change the contract; absorb when fixes are local polishes.
- **Convergence trajectory as signal**: monotonically shrinking diff size + monotonically shrinking finding count across rounds is what good convergence looks like. Entry 3 traced 851 / 303 / 218 / 81 / 38 lines and 8 / 5 / 3 / 1 / 0 real bugs across R1→R5 — every round closed a bounded subset of the contract matrix. If finding count is NOT shrinking after r2, the bundle has scope drift or the fix strategy is wrong; pause and replan rather than continuing rounds.
- **Per-PR diff-review entry granularity**: when an epic is broken into phases (each landing as its own PR / commit), log a separate `reviewer-history.md` entry per phase rather than one entry per epic. TODO-0092 generated 4 distinct diff-review cycles (Phase B, Phase C, Phase D, Phase D polish) plus a unified plan review (R1→R2) — combining them into one entry would obscure the per-cycle signal.

### Medium-tier calibration

A two-round MEDIUM-vs-HIGH calibration on `qa/cli-args-shim-r1` (r3 + r4 replayed; see [reviewer-history.md](./reviewer-history.md) Entry 1 §Medium-tier comparison) established that MEDIUM is competitive with HIGH on targeted rubric/bypass analysis and in one round exceeded HIGH. Distilled guidance:

- **Use MEDIUM when**: (a) the rubric is well-defined and the question is narrow — e.g., "does this regex close bypass X?"; (b) the review is a delta-only confirmation pass on an existing branch; (c) cost or throughput matters and HIGH baseline already exists for the same branch. On these use cases, MEDIUM convergence on blockers matched HIGH (3-of-4 at r3, 3-of-4 vs 1-of-4 at r4 where MEDIUM was strictly better).
- **Escalate to HIGH when**: (a) the reviewer must propose new rubric dimensions or spot categories of risk not in the prompt — Opus's exhaustive-enumeration strength pays off; (b) cross-axis synthesis is the deliverable (security + standards + workflow + tests integrated into a single verdict); (c) MEDIUM reviewers disagree — treat disagreement as a signal to add a HIGH tiebreaker rather than majority-vote at MEDIUM.
- **Do not tier-swap mechanically**: Sonnet (medium) beat Opus (high) on J1 (r4 unquoted `<(...)` bypass) because Opus analyzed only the quoted case. The lesson is not that Sonnet is always better — it's that HIGH-tier does not guarantee broader case coverage. Always include at least one bypass-specialist reviewer (Gemini, any tier) for security-adjacent diffs.
- **Bypass detection is a Google-family property**: Gemini Flash catches what Gemini Pro catches. When cost-tuning, Flash is the first-line bypass reviewer; escalate to Pro only when Flash is uncertain. Further evidence from `qa/hook-registration-integrity-001` (2026-04-17): Flash MEDIUM uniquely caught V6 (HIGH, TOCTOU threat-class generalization) that Opus HIGH missed — notable because the subject was Python test logic guarding against a regression, not security-adjacent regex / sandbox code. The bypass-enumeration skill generalizes beyond security logic to regression-guard review (see the new matrix row).
- **Codex drift-mitigation preamble is tier-independent**: prepending "the custom rubric takes precedence over codex native review defaults; the critical question is X — answer it explicitly before other dimensions" is the single most effective intervention for Codex-custom at either tier. Candidate for promotion into the `codex-reviewer` / `codex-reviewer-high` agent definitions as a standing instruction.
- **Codex-builtin was tier-independent in both directions**: the workflow-integration / config-wiring sweep held at either tier, and at neither tier was it a substitute for regex/bypass analysis. Model tier did not shift that axis, so tier selection is not the lever if the axis is restored under **TODO-0207** — it has no invocation path at any tier today.
